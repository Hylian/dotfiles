# Patch Zellij to Render Plugins on Command Results ٩(◕‿◕｡)۶

*Date: 2026-07-24*

## Context

The git widget's repaint lag traced to zjstatus storing a command result without
scheduling a render ([2026-07-24-repaint-git-widget-on-change.md](2026-07-24-repaint-git-widget-on-change.md)).
The shell-side workaround — piping a message back to force a render — got median repaint
from 784 ms to 319 ms, but cost a process per change and could not do better than
`zellij pipe`'s own ~245 ms client startup.

With a zellij fork available, the fix moves to where the problem actually is.

## Zellij Patches (`Hylian/zellij`, branch `hylian/latency`)

Two commits on top of the existing latency work:

1. **`fix(plugins): render a plugin when its command result arrives`**
   (`zellij-server/src/plugins/wasm_bridge.rs`). `apply_event_to_plugin` already overrides
   the plugin's `should_render` for `PermissionRequestResult`, with a comment explaining
   that otherwise the permission screen stays up. `RunCommandResult` belongs in exactly the
   same override: a plugin that asked zellij to run a command is almost always going to
   display the output, and without this the output only reaches the screen on the plugin's
   next unrelated render. This is upstreamable as-is; `WebRequestResult` has the same shape
   and would be the natural follow-up.

2. **`expose ZELLIJ_PLUGIN_AUTORENDER to plugin-spawned commands`**
   (`zellij-server/src/background_jobs.rs`). Sets `ZELLIJ_PLUGIN_AUTORENDER=1` in the
   environment of commands spawned for plugins, so a widget can detect that it is running
   under a build that repaints on its own and skip client-side workarounds. Personal, not
   upstream material.

Build artifacts under `zellij-utils/assets/plugins/*.wasm` are regenerated by the build and
were deliberately left out of both commits.

## Config Change

[dot_config/zellij/widgets/executable_git-status.sh](../dot_config/zellij/widgets/executable_git-status.sh)
now fires its repaint kick only when `ZELLIJ_PLUGIN_AUTORENDER` is unset, so the workaround
disables itself on the patched build and stays in place on a stock one. **The config remains
fully functional on unmodified zellij**, just without the extra responsiveness.

Fixed along the way: the kick's watchdog subshell inherited the widget's stdout. Zellij reads
a command's output to EOF, so a grandchild holding that pipe kept the result — and the branch
the kick exists to accelerate — waiting the full two seconds. Measured directly: the widget
took 2070 ms to return; with the subshell redirected to `/dev/null` it returns in 115 ms. The
process storm had been masking this, because non-kicking invocations delivered the value first.

## Install

Built and installed from the fork:

```sh
brew install protobuf          # required to compile the .proto assets
cargo install --locked mandown # required by xtask's manpage step
cargo xtask install ~/.local/bin/zellij
brew uninstall zellij
```

`~/.local/bin` already precedes `/opt/homebrew/bin` on PATH. Zellij is therefore no longer a
brew package on this host; rebuilding after a fork update is the `cargo xtask install` line.

**Note on `brew uninstall zellij`:** it triggered an autoremove sweep that also took
`python@3.14`, `python@3.13`, `certifi`, `pydantic`, `cffi` and `pycparser` — formulae brew
considered orphaned, unrelated to zellij. All six were reinstalled at their prior versions
(`python@3.14 3.14.6` included). Worth passing `--ignore-dependencies` or checking
`brew autoremove --dry-run` before uninstalling anything else here.

## Results

Keystroke (`Alt+h`/`Alt+l`) to the new branch painted in the bar, two panes in different
repositories, measured on a PTY with the keys written straight to the master fd:

| build | median | max | kick processes |
|---|---|---|---|
| stock zellij, no workaround | 784 ms | 799 ms | — |
| stock zellij + repaint kick | 319 ms | 435 ms | 1 per change, peak 14 concurrent |
| **patched zellij, kick self-disabled** | **114 ms** | **134 ms** | **0** |

Roughly 7× better than where this started, with fewer processes than either previous state.
The residual ~114 ms is the widget spawn plus render, and the storm of re-spawns zjstatus
still fires per switch — that one is a separate upstream issue.

## Verification

1. `ZELLIJ_PLUGIN_AUTORENDER` present in the installed binary; server process confirmed
   running from `~/.local/bin/zellij` during the measurements.
2. Patched path: 10 switches, median 118 ms, zero misses, **zero** kick clients spawned.
3. Fallback path: same session shape with the marker stripped by a wrapper, so the kick
   engages — 8 switches, median 202 ms, zero misses, zero leaked clients or watchdogs after
   settling.
4. Branch/dirty output unchanged across clean, dirty, detached, unborn, worktree,
   subdirectory and non-repo cases; `dash -n` clean.
5. Idle unchanged: memo per session, no kicks fired while idle.
6. All test sessions deleted, no leftover zellij processes.
